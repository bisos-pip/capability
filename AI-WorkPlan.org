* Stage 1: Convert CBS from =.pcs= to Spread-Planted =cbmProc.spcs=

Goal: Introduce a spread-planted CS parallel to =bisos.dockerProc='s
=dockerProc.spcs=. In the CBM world the planted file is named
=cbmProc.spcs= (Capability Bundle Materialization Processor). One
=cbmProc.spcs= per capability leaf under the CBM tree; each declares
which capability it represents via =cbmProc_seedInfo.setup()=, inlines
its CBS content (=cba_seed.setup()= + flavor-specific =setup()= like
=cba_sysd_seed.setup(sysdUnitsList=[...])=), and gates materialization
via a sibling =cbmProc.control= file.

** Design Decisions Captured Before Stage 1 Begins

1. *Uniform filename =cbmProc.spcs=.* Every capability leaf has the
   same-named =.spcs=. Which capability it represents (airflow,
   nextcloud, ...) is declared *inside* via
   =cbmProc_seedInfo.setup(capabilityName="airflow", ...)=. Parallel
   to how every docker leaf has the uniform =dockerProc.spcs=.

2. *=cbmProc.spcs= inlines the CBS content* (Q1 = inline). Replaces
   today's =airflow-cbs.pcs=. The sub-=.pcs= files
   (=airflow-sbom.pcs=, =airflow-db-sysd.pcs=, etc.) stay where they
   are and are referenced by string name from inside =cbmProc.spcs=.

3. *=cbmProc.control= file gates whether materialization runs.*
   Values: =available= / =enabled= / =disabled= (Q2 = start with
   these three, refine later).
   - =available= --- present, not yet activated; walker skips.
   - =enabled= --- walker materializes (idempotent).
   - =disabled= --- passive; walker skips. No auto-un-materialize.
     User must explicitly run =cbs_unMaterialize= to tear down.

4. *=cbmProc.status= file records last materialization outcome.*
   Machine-written by the seed after each =cbs_*= verb.

5. *Control/status shape --- start with plain-text files, not JSON*
   (Q3 + Q4 + Q5 = "not JSON, refine later"). Simple one-line files
   for the first cut; may promote to directory-with-aspects later if
   state grows. Format TBD but not JSON.

6. *Verb families --- both, orthogonal* (Q6 = =cbm_*= alongside
   =cbs_*=):
   - =cbs_*= (existing) --- specification lifecycle:
     =cbs_load=, =cbs_sbom=, =cbs_assemble=, =cbs_materialize=,
     =cbs_reMaterialize=, =cbs_unMaterialize=, =cbs_deMaterialize=,
     =cbs_type=, =cbs_isMaterialized=.
   - =cbm_*= (new) --- control/status layer:
     =cbm_enable=, =cbm_disable=, =cbm_available=, =cbm_isEnabled=,
     =cbm_status=, =cbm_control= (raw write).

7. *Control-file gate lives in =cbmProc-seed.cs=* (Q5). Before
   dispatching any =cbs_*= verb, the seed reads =cbmProc.control=
   from the plant path. If not =enabled=, log + record in
   =cbmProc.status= + short-circuit. Individual =cbmProc.spcs= files
   don't repeat the check. =cbm_*= verbs bypass the gate (they
   *are* the gate control).

8. *Planted =cbmProc.spcs= calls =plantWithWhich("cbmProc-seed.cs")=*
   (Q7). Not =cba-sysd.cs=. =cbmProc-seed.cs= is the CBM-aware seed
   that composes =cba_csu= + =cba_sysd_csu= + a new =cbmProc_csu=
   (the control/status verbs) and adds the gate.

** Design Pivots During Implementation

Three material pivots from the original design decisions above happened
during Stage 1 execution. Recorded here so future-Claude doesn't
re-litigate:

- *D4 pivot (leaf =.spcs= body): "inline the CBS content" was wrong.*
  Original decision said the =cbmProc.spcs= at each leaf should inline
  =cba_seed.setup(...)= + =cba_sysd_seed.setup(sysdUnitsList=...)=.
  That duplicates content already present in the CBS file
  (e.g. =/bisos/asc/web/bin/airflow-cbs.pcs=). The corrected design:
  =cbmProc.spcs= is a *pointer* to the CBS executable via a =cbsSpec=
  field (=capabilityName= + =cbsSpec= only). At =cbm_materialize= time,
  CBM subprocess-invokes the CBS. Load-bearing principle:
  *CBM sits on top of CBS; does not duplicate it.*

- *D7 pivot (gate location): "gate in =cbmProc-seed.cs=" was ugly.*
  Original decision put the control-file gate check in the seed's
  =__main__= block (before =g_csMain=), with =sys.exit(0)= on skip.
  Problem: produced =SystemExit: 0= traceback noise. Corrected:
  gate lives in each Family-2 Cmnd body (=cbm_materialize= etc.) via
  =controlRead(plantDir)=. Family-1 verbs (=cbm_enable= etc.) bypass
  naturally because they don't call =_dispatchCbs()=.

- *D8 pivot (planting mechanism): don't call =cba_sysd_seed.plantWithWhich=.*
  Original template called
  =cba_sysd_seed.plantWithWhich("cbmProc-seed.cs")=. But
  =cba_sysd_seed.plantWithWhich()= is hardcoded to accept only
  =cba-sysd.cs= (silently returns for any other value). Corrected:
  =cbmProc.spcs= imports =cbmProc_seed= (which registers atexit for
  =cbmProc-seed.cs= via its own registrar) --- no call to
  =cba_sysd_seed.plantWithWhich= at all.

** Verb-family clarification (added during implementation)

The =cbm_*= verb family expanded beyond the original "control/status
layer" to include a *materialize* sub-family that subprocess-invokes
the CBS. Final structure:

- Family 1 (control/status, never gated): =cbm_control=, =cbm_status=,
  =cbm_isEnabled=, =cbm_enable=, =cbm_disable=, =cbm_available=.
- Family 2 (materialize, gated, subprocess-dispatch): =cbm_materialize=,
  =cbm_reMaterialize=, =cbm_unMaterialize=, =cbm_sbom=. Each calls
  =_dispatchCbs(verb)= which checks gate + resolves cbsSpec +
  =subprocess.run([cbsExec, '-i', verb])= + writes status.

The =cbs_*= verbs (from =cba_csu=) remain in the csuList but are NOT
the leaf's public interface --- =walkExamples()= advertises only
=cbm_*=.

Key behavior --- the *control-file gate*:

Before dispatching a =cbs_*= verb, read =cbmProc.control= via
=cbmProc_seedInfo.controlRead()=. If value is NOT =enabled=:
1. Emit an =ann.note= that the CBM is skipped (with the current
   control value).
2. Update =cbmProc.status= with a one-line "skipped: control=<value>
   at <timestamp>" record.
3. Return success (short-circuit --- not an error, this is the
   declared intent).

If value IS =enabled=: dispatch normally. After the dispatched Cmnd
returns, write outcome to =cbmProc.status= (success/failure +
timestamp + verb name).

=cbm_*= verbs bypass the gate --- they *are* how the user
manipulates the gate.
